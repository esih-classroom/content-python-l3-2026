Pourquoi ce cours vous demande ça

Vous ne rendrez pas des fichiers dans ce cours, vous rendrez des projets. Un projet Python, ce n'est pas un .py isolé : c'est un dossier avec le programme, la liste des bibliothèques dont il a besoin (pyproject.toml), et les versions exactes de ces bibliothèques (uv.lock). C'est ce qui permet à l'enseignant de reconstruire votre environnement à l'identique avec une seule commande et d'obtenir le même résultat que vous.

Envoyer ça par courriel ou en archive ne marche pas : il manque toujours un fichier, ou l'archive pèse 200 Mo parce qu'elle contient un dossier qui n'avait rien à y faire. Git règle le problème une fois pour toutes.

Ce que vous devez savoir avant de continuer : Git n'est pas au programme de ce cours. Il ne figure dans aucun résultat d'apprentissage, il n'est évalué nulle part, et personne ne vous demandera de faire un rebase. Vous en apprenez ici le strict nécessaire pour rendre votre travail. Cette page est un mode d'emploi, pas un chapitre.

Cela dit, vous en aurez besoin dans à peu près tous les emplois de développeur qui existent. Autant commencer maintenant, dans un cadre où une erreur ne coûte rien.

1. Six mots à comprendre

C'est tout le vocabulaire dont vous avez besoin.

Mot Ce que c'est
Dépôt (repository, « repo ») Un dossier de projet dont on garde l'historique. Votre dossier de travail, plus sa mémoire
Commit Une photo de l'état du projet à un instant, avec un message qui dit ce que vous venez de faire. C'est l'unité de base : on ne sauvegarde pas un fichier, on enregistre un état
Historique La suite des commits. On peut y revenir, comparer deux états, voir qui a écrit quoi et quand
Distant (remote) La copie du dépôt qui vit sur GitHub. La vôtre est sur votre machine ; les deux se synchronisent quand vous le demandez
Issue Un fil de discussion attaché au dépôt. Dans ce cours, chaque travail à rendre est une issue - l'énoncé y est écrit, et vous la fermez pour remettre
Pull request (PR) Une proposition de modification, avec une discussion ligne par ligne. Dans ce cours, c'est là que l'enseignant écrit ses remarques sur votre code

Deux précisions qui évitent des malentendus :

  • Git et GitHub ne sont pas la même chose. Git est le programme qui gère l'historique, sur votre machine, hors connexion. GitHub est un site qui héberge des dépôts Git et ajoute autour des issues, des pull requests, des permissions. Vous pouvez utiliser Git sans GitHub. Ici, vous utiliserez les deux.
  • Un commit n'est pas une sauvegarde automatique. Rien ne part tant que vous ne le demandez pas. C'est déroutant au début, et c'est aussi ce qui fait que vous contrôlez exactement ce que l'enseignant voit.

2. Créer votre compte GitHub

À faire maintenant, avant la séance 1 - sans compte, vous ne pouvez rien recevoir.

  1. Allez sur github.com/signup
  2. Choisissez un nom d'utilisateur. Il sera visible par tout le monde et vous le garderez des années. Prenez votre nom, ou une variante lisible : jsaintil, ana-pierre. Évitez xX_dark_coder_Xx, vous le regretterez au premier entretien d'embauche
  3. Utilisez une adresse de courriel que vous consultez : les notifications du cours y arriveront
  4. Activez la double authentification quand GitHub vous le propose. C'est obligatoire sur GitHub, et vous serez bloqué plus tard si vous la reportez
  5. Envoyez votre nom d'utilisateur à l'enseignant, par le canal indiqué en séance

Le compte est gratuit et le restera. Vos dépôts de cours sont privés : seuls vous et l'enseignant les voyez.

3. Deux façons de travailler - choisissez la vôtre

Les deux sont acceptées toute l'année, et vous pouvez passer de l'une à l'autre.

Voie A - Git installé sur votre machine

C'est la voie normale si vous avez un ordinateur. Vous travaillez dans VS Code, comme pour le reste du cours.

Installer Git

Système Comment
Windows git-scm.com/download/win, installateur, tout par défaut
macOS xcode-select --install dans le Terminal
Linux sudo apt install git, ou l'équivalent de votre distribution

Vérifiez, puis dites à Git qui vous êtes - ces deux lignes ne se font qu'une fois dans votre vie :

Terminal
bash
123
git --version
git config --global user.name "Votre Nom"
git config --global user.email "votre.adresse@exemple.com"

Mettez la même adresse que sur GitHub, sinon vos commits ne seront pas reliés à votre compte.

Voie B - Tout dans le navigateur

Rien à installer, et ça marche sur téléphone. Vous ne tapez aucune commande Git : vous ouvrez la page de votre dépôt sur GitHub, vous téléversez ou modifiez vos fichiers, et c'est fait.

C'est la voie prévue pour ceux qui n'ont pas d'ordinateur personnel. Elle n'est pas un rabais : vous rendez exactement le même dépôt et vous êtes noté exactement pareil. La page « Travailler sans ordinateur » de ce module détaille la marche à suivre.

4. Le déroulé d'un travail, du début à la fin

Cinq étapes, les mêmes toute l'année.

1. Vous recevez le dépôt

Quand l'enseignant publie un travail, Classmoji crée un dépôt privé à votre nom, à partir d'un modèle. Vous recevez un lien. Le dépôt contient déjà l'énoncé, les fichiers de départ, et une issue qui décrit ce qui est attendu.

Vous ne créez jamais de dépôt vous-même dans ce cours.

2. Vous le récupérez

Voie A :

Terminal
bash
12
git clone https://github.com/ORGANISATION/tp1-votre-nom.git
cd tp1-votre-nom

git clone copie le dépôt sur votre machine, avec tout son historique. Vous ne le faites qu'une fois par travail.

Voie B : rien à faire, vous travaillez directement sur la page du dépôt.

3. Vous travaillez

Comme d'habitude : uv run, VS Code, les exercices du cours. Codez, testez, faites tourner.

4. Vous enregistrez et vous envoyez

Voie A :

Terminal
bash
1234
git status                        # que s'est-il passé depuis la dernière fois ?
git add .                         # je prépare tout ce qui a changé
git commit -m "Traduction du programme et notes"
git push                          # j'envoie sur GitHub

Faites-le plusieurs fois pendant votre travail, pas une seule fois à la fin. Un commit toutes les demi-heures, avec un message qui dit ce que vous venez de faire. C'est votre filet de sécurité : tant que vous n'avez pas poussé, votre travail n'existe que sur votre machine.

Voie B : sur la page du dépôt, Add file → Upload files, puis un message et Commit changes. Le commit se fait dans le navigateur.

Vérifiez toujours que vos fichiers sont bien visibles sur la page GitHub du dépôt. Si vous ne les voyez pas là, l'enseignant ne les voit pas non plus.

5. Vous remettez

Fermer l'issue du travail, c'est remettre. Tant que l'issue est ouverte, le travail n'est pas rendu, même si votre code est poussé. Tant qu'elle est fermée, il est rendu, à l'heure de la fermeture.

Écrivez un dernier commentaire dans l'issue si vous avez quelque chose à signaler - un point que vous n'avez pas réussi, un choix que vous voulez expliquer - puis fermez-la.

Et ensuite : le retour

L'enseignant ouvre une pull request de retour sur votre dépôt. Ses remarques y sont attachées aux lignes concernées de votre code. Allez la lire : c'est là que se trouve l'essentiel de ce que vous avez à gagner, bien plus que dans la note.

5. Les six commandes, et rien d'autre

Voie A uniquement. Affichez cette table à côté de vous les premières semaines.

Commande Ce qu'elle fait Quand
git clone <lien> Récupère un dépôt sur votre machine Une fois par travail
git status Dit ce qui a changé et ce qui est prêt à partir Tout le temps. En cas de doute, c'est la réponse
git add . Prépare tout ce qui a changé Avant chaque commit
git commit -m "message" Enregistre un état, avec sa description Plusieurs fois par séance de travail
git push Envoie vos commits sur GitHub Après chaque commit, ou groupés
git pull Récupère ce qui a changé sur GitHub Si l'enseignant a modifié le dépôt

Vous n'aurez besoin de rien d'autre cette année. Si un tutoriel vous parle de branches, de merge ou de rebase, c'est utile et intéressant - ce n'est pas nécessaire ici.

Sur les messages de commit. Une phrase courte qui dit ce que vous venez de faire : Traduction littérale du programme C++, Réécriture avec zip et f-strings, Ajout de NOTES.md. Pas update, pas fix, pas .. Ce sont vos propres notes, et vous les relirez.

6. Ce qu'on ne met jamais dans un dépôt

Un dépôt contient votre travail, pas ce qu'une machine peut régénérer.

À ne jamais envoyer Pourquoi
.venv/ Des centaines de mégaoctets, reconstructibles en une commande. C'est la faute n° 1
__pycache__/ Généré automatiquement par Python
Fichiers de données volumineux Sauf si l'énoncé le demande explicitement
Mots de passe, jetons, clés Un dépôt garde tout dans son historique. Ce qui y entre une fois y reste

Bonne nouvelle : uv s'en occupe déjà. Quand uv crée l'environnement .venv/ d'un projet, il y dépose un fichier qui dit à Git de l'ignorer entièrement. Vous ne l'enverrez pas par accident, même sans y penser. Les dépôts modèles du cours ajoutent une règle pour __pycache__/.

Le réflexe qui vous protège reste le même : regardez ce que git status affiche avant de commiter. Si vous y voyez apparaître des dizaines de fichiers que vous n'avez pas écrits, arrêtez-vous et demandez.

7. Ce qui va coincer, et quoi faire

« GitHub me demande un mot de passe et le refuse »

Normal : GitHub n'accepte plus les mots de passe pour envoyer du code. Trois solutions, de la plus simple à la plus manuelle :

  1. Passez par VS Code. Il propose de vous connecter à GitHub et gère l'authentification tout seul. C'est de loin le plus simple, et vous avez déjà VS Code
  2. Installez GitHub CLI (cli.github.com) et lancez gh auth login. Une fois, et c'est réglé
  3. Créez un jeton d'accès personnel dans les réglages GitHub (Settings → Developer settings → Personal access tokens) et utilisez-le à la place du mot de passe. À faire seulement si les deux premières ne marchent pas

« Updates were rejected »

Le dépôt sur GitHub contient quelque chose que vous n'avez pas. Faites git pull, puis git push. Si Git vous demande de résoudre un conflit et que vous ne savez pas quoi en faire, ne bricolez pas : demandez. Un conflit mal résolu perd du travail.

« J'ai poussé, mais l'enseignant ne voit rien »

Trois causes, dans l'ordre de fréquence : vous avez commité sans pousser ; vous avez travaillé dans le mauvais dossier ; vous n'avez pas fermé l'issue. Ouvrez la page du dépôt sur GitHub - ce que vous y voyez est exactement ce que l'enseignant voit.

« J'ai tout cassé »

Vous n'avez rien cassé. Git conserve l'historique : tant que vous avez commité, l'état précédent existe encore. Ne supprimez pas le dossier, ne recréez pas de dépôt, n'effacez rien. Écrivez dans l'issue ce que vous avez fait, et attendez.

Pas de connexion au moment de rendre

Vos commits restent sur votre machine et partiront au premier git push avec du réseau. Utilisez un token de report - le cours vous en donne, justement pour ça. Le mode d'emploi est sur la page « Comment fonctionne ce cours ».
